# UI / UX・画面・タイトル

[PRO_QUALITY_BIBLE.md](PRO_QUALITY_BIBLE.md) の判断基準が優先する。デザインの方向性（配色・画風・レイアウトの大きな変更）はユーザーの採用判断の後に着手する。スチームパンク系（歯車・真鍮）のUIは不採用。

- 文字の大きさ・コントラスト・色だけに頼らない表現・動きの配慮の基準は [ACCESSIBILITY.md](ACCESSIBILITY.md)。
- UIの配色の現状と未決定の事項は [ART_DIRECTION.md](ART_DIRECTION.md) §7。
- ここの秒数・px は現在のゲームを基準にした目安（PRO_QUALITY_BIBLE §1.3）。

---

## 1. 原則

- UIは常にゲーム演出との関係で考える。UIの見た目・動きがゲーム全体の質感と合っていること。
- **作りかけに見える画面を残さない。** 真っ暗な画面の端に小さな文字とボタンがあるだけ、のような画面はプレイヤーに「未完成」と伝わる。
- 画面ごとに「見出し」「今やること（主ボタン）」「戻る」の位置をそろえる。
- 突然出現・消滅させない。重要な表示は短いフェード・スライドで出す。ただし、すべての画面に動きを付けることを目的にしない（§15）。

---

## 2. 1280×720での読みやすさ

- 読ませる文字は14px以上（論理ピクセル）。補足でも12px未満にしない。
- 14pxは論理ピクセルの値。1920×1080などで実際に何px相当になるかは、実際の画面で測って評価する（[ACCESSIBILITY.md](ACCESSIBILITY.md) §1）。論理14pxを機械的に18pxへ変えない。
- 文字と背景のコントラストは [ACCESSIBILITY.md](ACCESSIBILITY.md) §2（標準の文字4.5:1、大きい文字3:1。背景が変わる所は最も条件の悪い所で測る）。
- **絵の上に文字を直接置く時は、必ず下地（半透明の帯）か縁取り・影を付ける。** 明るい部分（松明・炎・空）に文字を重ねない（ボス作成トップの説明文は松明に重なって読めない）。
- 大事な情報（戦闘結果・エラー・確認）をスクロールの奥に隠さない。収まらない時は表示の仕方を変える。
- 英語は日本語より長くなる。英語表示でボタンや欄からはみ出さないか確認する。
- UIが画面を占有しすぎていないか。戦闘中は戦場が主役。

---

## 3. 操作の手応え

- ボタンは normal／hover／pressed／focus／disabled の見た目を持つ。押せないボタンは押せないと分かる見た目にする（灰色だけに頼らない。§13）。
- キーボードでフォーカスを動かした時、フォーカスの位置が見えること。hover と focus を区別できること。
- クリック・ホバーのSEは `RBMAudio.bind_ui`（ゲームルートが全ボタンに自動で付ける）を使う。個別に鳴らす場合は自動の音を止める（`set_meta("rbm_audio_bound", true)`、タイトルのSTARTの前例）。
- UIのアニメーションは0.12〜0.25秒（目安）、出る時は ease-out、消える時は ease-in。等速（linear）は小さな明るさの変化だけにする。
- 二重押しで処理が2回走らないようにする（タイトルのSTARTの `_starting` の前例）。

---

## 4. 画面遷移

- 現状、ホーム⇔ボス作成⇔挑戦⇔戦闘の切り替えは表示の切り替えだけで、つなぎの動きがない（タイトル→ホームの0.18秒フェード、ホームのモニターの拡大だけが例外）。
- 大きな画面の切り替えには短いフェード（0.15〜0.3秒）を入れる。フェード中は入力を受け付けない。
- 遷移の動きは「どこからどこへ移ったか」を分からせるために使う。飾りだけの動きを足さない（§15）。
- 遷移で待たせない。ロードが必要なら先に読み込む。

## 5. 戦闘画面（HUD）

### 5.1 現状のレイアウト
左上: ボス名とターン／REWIND（TEST BATTLE）・やり直し（挑戦）。右上: 行動順・LOG・終了。右下: コマンド。下: 味方のHP/SP。戦場の左下: 最新の行動と結果の文字。

### 5.2 守ること
- **結果は全員分読めること。** 全体攻撃の結果が表示欄（高さ112pxのスクロール）からあふれて隠れないようにする。
- 命中した対象の近くに、ダメージ・回復の手がかりを出す（現状は数字のポップアップがない）。数字を出すかどうかはデザイン判断。
- ボスの残りHPの見せ方はゲームデザインの判断（現状は表示なし）。表示しない場合も、ボスが弱っていることが見た目で分かる工夫を検討する。
- 結果画面（勝利・敗北）は決着の瞬間。小さなパネルだけで終わらせない（見出し・余韻・結果の要約）。勝利と敗北でパネルの位置・作りをそろえる。
- 大技の間、HUDがVFXを隠しすぎる場合は、HUDを一時的に薄くする・下げることを検討する（演出の邪魔をしない）。

## 6. ボス作成（Creator）

- 道具の画面でも、完成した製品の画面に見えること。STEPの見出し・左の工程一覧・右のBOSS PROFILEの配置は全STEPで統一されている（維持する）。
- クリアチェックの開始画面・保存画面は、他のSTEPと同じ作り（見出し・説明・主ボタンの配置）にする。
- 入力欄の範囲・既定値・エラーは、その場で分かるようにする（HPの範囲1〜99,999のような上限は入力欄で止める）。

---

## 7. タイトル画面（Codex担当）

タイトル画面はゲームの第一印象なので特に厳しく評価する。見た目・演出の変更はCodexの担当で、Claude Codeは技術的な修正だけを依頼に応じて行う。

### 7.1 現在の仕様（2026-10時点）
- 起動ごとにボスの部屋を1つ選ぶ（武者・紳士・宇宙飛行士、同じ起動中は固定）。部屋は `title_rooms/` に登録された承認済みのものだけ。
- 共通シェル `rbm_boss_room_title.gd` が、正式な文字ロゴ（`RBMTitleBootPreview` の TitleText、Oxanium 36px）・START・入力・0.18秒のフェードを持つ。部屋は絵と動きだけを持つ。
- START: 画面のどこでも左クリック／タッチ／Enter／Space。押すと決定音1回→0.18秒でホームへ。待ち時間なし。
- 宇宙飛行士の部屋の壁時計はPCの現在時刻と同期（等速）。

### 7.2 確認する項目
キャラの待機アニメーション／重心／Secondary Motion／背景／ライティング／奥行き／環境の動き／ロゴ／UI／ループ（ループ点のつなぎ目）／構図／シルエット／不自然な変形／機械的なTween感（[ANIMATION_CRAFT.md](ANIMATION_CRAFT.md) §13・§14）。
- ループ点で絵が飛ばないこと（36秒・40秒のループのつなぎ目を必ず見る）。
- 部屋の作成で画面を止めない（目安0.2秒以内。紳士の部屋は高速化前2秒以上止まっていた）。
- 音がない（BGM・環境音なし）のは現状の課題（[AUDIO.md](AUDIO.md)）。

## 8. オンライン・Loading・エラー

- 通信中は「待っている」ことが分かる表示を出す（`RBMLoadingState` は状態管理だけで、表示はまだない）。
- エラーは人が読む文にする。`network_error`・`invalid_payload` のような内部コードをそのまま見せない（必要なら小さく添える）。
- 0件・取得失敗・再試行の状態にも、整った見た目を用意する。

---

## 9. 翻訳（日本語／英語）

- 画面に出る文字はすべて `tr()`／`TranslationServer.translate()` を通し、`localization/ui_strings.csv` に英語を用意する。
- ボスの外見名・技名・マスターデータの表示名も対象（現状、元からいるボス6体の名前・覚醒まわりの表示・タンクの技名が未翻訳）。
- 日本語の画面に英語を混ぜない（例:「Creatorに戻る」）。固有名詞として残す場合は全画面で統一する。
- CSVを変えたら `.translation` を作り直す（Godotで取り込む）。

## 10. 製品としての基本

- 設定: 音量（全体・BGM・SE）、ウィンドウ／全画面、言語。光の点滅を弱める設定も検討する。現状、設定画面はない。
- 起動スプラッシュとアプリのアイコンを自作のものにする（現状は未設定でGodotの既定）。
- 入力: マウス・キーボードは対応済み。ゲームパッドは未対応（`ui_accept` にパッドのボタンが入っていない）。対応する場合は、タイトルだけでなく全画面のボタンを `ui_accept` で操作できるようにするのが自然（プロジェクトの入力設定の変更はユーザー判断）。
- 1280×720より大きいウィンドウ・違う比率（黒帯）・縮小でも崩れないこと。
- 1920×1080の全画面は1.5倍の拡大（`canvas_items` の既定の拡大）なので、1px格子のキャラは画素の幅が1pxと2pxで不ぞろいになる。整数倍の拡大に切り替えるかは、黒い余白とのかね合いでユーザーが決める（[QUALITY_AUDIT.md](QUALITY_AUDIT.md) QA-14）。

### 10.1 表示モードと拡大方式を決める手順
**「ドット絵だから integer にする」と自動で判断しない。** 比較画像と実際の画面をユーザーに見せて決める。今の構成（論理1280×720、`canvas_items`、拡大は既定の fractional）を勝手に変えない。

分かっている事実（Godot 4.7 の公式ドキュメント `[GD1]` `[GD2]`）:
| 項目 | 内容 |
|---|---|
| fractional | 任意の倍率で拡大する（1.5倍など）。最近傍の画像は、非整数倍では画素の幅が不ぞろいになる |
| integer | 倍率を整数へ切り捨て、残りは黒帯（Godot 4.2以降）。画素の不ぞろいを防ぐ |
| 1280×720 を integer で表示した場合（計算） | 1920×1080 → 倍率1（1280×720のまま周囲が黒帯）、2560×1440 → 2倍、3840×2160 → 3倍（黒帯なし） |
| Fullscreen | 複数ウィンドウに対応し、表示モードを変えない。Windowsでは下端に1pxの線が残る |
| Exclusive Fullscreen | 1画面1ウィンドウ。ドキュメントはゲームにはこちらを推奨。録画ソフトで撮れない場合がある |
| 切り替え時 | ドライバによって、全画面の切り替えで一瞬暗くなることがある |

比較の手順:
1. 同じ場面を用意する（大技のある戦闘、Creator のSTEP、オンライン一覧、タイトル、結果画面）。
2. 次の組み合わせで撮る: 1280×720ウィンドウ／1920×1080 fractional（今の作り）／1920×1080 integer（黒帯）／2560×1440／必要なら最大化ウィンドウ。全画面の種類（Fullscreen／Exclusive Fullscreen）ごとに、録画ソフト（商品ページの動画を撮る道具）で撮れるかも確かめる。
3. 比べる: キャラの画素の不ぞろい（拡大した切り抜き）、黒帯の面積、文字の実寸と読みやすさ（ACCESSIBILITY §1）、全画面の効果の重さ（PERFORMANCE §1、大きい画面ほど重い演出がある）。
4. 比較画像と気づいた点をユーザーに見せる。決めるのはユーザー。決まるまで `project.godot` の表示設定は変えない。
- 基準解像度そのもの（1280×720）を変える案は、全UI・全演出に影響する大きな変更なので、ユーザーが求めた時だけ検討する。

## 11. 画風の統一

- 戦闘・タイトル・キャラはドット絵。ボス作成のトップ・モード選択・挑戦ハブの背景は細密な絵で、画風が違う。新しく画面の背景を作る時は、どちらに合わせるかをユーザーと決めてから作る。
- フォント: 同梱しているのは英字用の Oxanium（タイトルのロゴ）と Rajdhani（STARTなど）だけ。**日本語は専用フォントを同梱しておらず、OSのフォントへの自動フォールバックで表示している**ため、PCによって見た目が変わり、日本語フォントの無い環境（Steam Deck／Linux等）では文字が出ない恐れがある（[QUALITY_AUDIT.md](QUALITY_AUDIT.md)）。フォントの追加・変更はユーザーの判断で行う。

---

## 12. Visual Hierarchy と Primary／Secondary Action

- 画面ごとに、**主な行動（Primary action）を1つ**決める。一番目立つのはそのボタン。それ以外（Secondary action）は控えめにする。
- 目立たせ方は、大きさ・明暗差・位置・まとまりで作る。色だけで区別しない（ACCESSIBILITY §3）。
- 主ボタンと「戻る」の並び順・位置を全画面でそろえる（今はクリアチェック開始画面が「戻る｜開始」、保存画面が「保存する｜戻る」で逆。QA-12）。
- 削除・上書きなどの破壊的な行動は、主ボタンと見分けられる見た目にし、初期のフォーカスを置かない。
- 見出し → 説明 → 選択肢 → 主ボタン、の順で目が動くか（1コマ止めて確かめる。Review I）。

## 13. 状態の見せ方

| 状態 | 守ること |
|---|---|
| Focus | フォーカスが見える。hover と区別できる。画面を開いた時の初期フォーカスは、最もよく使う安全な行動に置く |
| Disabled | 押せないと分かる。灰色だけに頼らず、必要なら理由の文やアイコンを添える。文字のコントラストは3:1以上（ACCESSIBILITY §2） |
| Loading | 待っていることが分かる表示を出す。止まって見える画面を作らない（§8、QA-23） |
| Empty | 0件の時も、何が起きているか・次に何をすればよいかが分かる整った表示にする |
| Error | 人が読める文で、何が起きたかと、どうすれば戻れるか（再試行など）を示す（§8） |
| Error prevention | 入力はその場で範囲を確かめる（§6）。できない操作は、押してから失敗させるより、押せない理由を先に示す |
| Destructive | 削除・保存せずに終了・上書きは、結果を言葉で示す確認を出す（例: 「この操作は取り消せません」）。確認の初期フォーカスは安全な側に置く |
| Confirmation | 保存・公開など大事な操作の後は、成功したことを短く伝える |

## 14. ナビゲーション

- **キーボード**: マウスを使わずに全機能へ届くこと。フォーカスの移動順が見た目の並びと一致していること。Enter／Space で決定、Esc で戻る（戻れる画面）。現状、全画面のフォーカス順の確認は未実施。
- **ゲームパッド（将来、対応すると決めた場合の基準）**: `ui_accept`／`ui_cancel` にパッドのボタンを割り当てる。十字キー・スティックでフォーカスが動く。マウスのホバーでしか見られない情報を作らない。戦闘の対象選択もパッドでできる。画面にボタンの絵を出す場合は、使っている機器のボタンと一致させる。対応するかはユーザーの判断（QA-29）。

## 15. UIのアニメーションの目的

アニメーションは次の目的の時だけ使う。
1. 状態の変化を伝える（押せるようになった、選ばれた、減った）
2. 視線を誘導する（今見るべき所）
3. 操作の結果を伝える（押した、保存した、失敗した）
4. 画面遷移を理解させる（どこからどこへ移ったか）

- すべての画面にアニメーションを付けることを目的にしない。目的のない飾りの Tween を増やさない。
- 文字のある画面の後ろで動き続けるもの・点滅するものは、見る人の負担になりうる（ACCESSIBILITY §4、`[X117]`）。

## 16. 文字の拡大と、色以外の手がかり

- 文字の拡大を将来できるように、文字サイズはテーマの定数に集め、欄が文字に合わせて伸びる作りにする（ACCESSIBILITY §1）。
- 状態・属性・結果を色だけで伝えない。文字・形・アイコン・位置・動きのどれかを併用する（ACCESSIBILITY §3）。
