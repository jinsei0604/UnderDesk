# パフォーマンス・構造・検証

[PRO_QUALITY_BIBLE.md](PRO_QUALITY_BIBLE.md) の判断基準が優先する。**演出の品質を上げるために処理落ちを増やすことは認めない。** 処理落ちはそのまま「カクつき」「弱いimpact」として見える（武者の着弾が承認動画より弱く見えた原因は、実時間で8〜16fpsに落ちていたこと）。

---

## 1. 予算（参照機での目安）

参照機: 現在の開発機（Intel UHD Graphics、`gl_compatibility`）。1280×720と1920×1080の両方で測る。

| 項目 | 目安 |
|---|---|
| 演出中の平均 | 58fps以上 |
| 33msを超えるフレーム | 0（意図した Hit Stop・暗転を除く） |
| 20msを超えるフレーム | 演出全体の2%以下 |
| 演出開始時の停止（初回の読み込み・シェーダーのコンパイル） | 33ms以下。初回も2回目以降と同じ時間で始まる（§2.1。停止を戦闘開始など別の瞬間へ移さない） |
| 待機中（オーラ・背景の動き） | 60fpsを保つ |
| 画面・タイトルの部屋の作成で止まる時間 | 0.2秒以内 |
| 演出中の描画対象（Performanceの objects） | 600前後まで（通常の戦闘は約240） |
| 演出中のドローコール | 300前後まで（通常の戦闘は約85） |

録画（`--write-movie`／`--fixed-fps`）でも、30fpsで見た時に不自然でないこと（動きの間引きで速さや当たりの瞬間が飛ばないこと）。

### 1.1 この予算の位置づけ
- 演出の秒数・揺れのpx などの「目安」と違い、この予算は**参照機での実測に基づく基準**で、Release Gate の「許容できない frame-time spike なし」の判定に使う（PRO_QUALITY_BIBLE §1.1・§1.3）。
- 予算を満たせない時は、実測の結果と理由をユーザーに示し、承認を得てから完成扱いにする。
- 参照機は性能の低い内蔵GPU。ほかのPC（専用GPU・Steam Deck など）での実測は、まだ行っていない。

### 1.2 改善と呼べるもの
- **見た目を削っただけでfpsを上げる対応は、改善とみなさない。** 同じ見た目（画素の比較）か、ユーザーが認めた同等以上の見た目を保ったまま速くする（[QUALITY_EVALS.md](QUALITY_EVALS.md) Eval F）。
- 見た目を変える必要がある時は、変える前後の一覧画像・動画をユーザーに見せて判断を求める。

## 2. 重くなる原因と対策（実測で分かっているもの）

| 原因 | 実例（2026-10の計測） | 対策 |
|---|---|---|
| 大きなテクスチャを再生のたびに読み込む | 紳士の着弾画像 2560×2240 ×3枚を単体・覚醒後の攻撃のたびに読み込み、開始0.11〜0.16秒で毎回110〜160ms停止 | ボスが決まった時点で裏で読み込み、戦闘の間保持（§2.1、QA-05で対応）。必要以上の解像度にしない |
| 初回だけの読み込み・シェーダーのコンパイル | 竜62ms、ゴースト47ms、武者77ms、武者の覚醒154ms、ヒーラーの全体回復47ms（2回目は消える） | 読み込み・デコード・解析は §2.1 の事前読み込み（QA-06。事前読み込みが終わった後は初回の開始 14〜19ms。間に合わない最速の経路は演出の開始の境界で素材が揃うまで待ち、開始 15〜17.5ms）。GPU側の初回の準備は §2.1 の最後の項目（原因を計測してから） |
| 1フレームに描き直す図形（`draw_*` の呼び出し）が多すぎる | タンクの決め技の土煙で描画対象が約250→約1,360、1フレーム42〜60ms（ドローコールは約85のまま）。侍のカウンターで描画対象 最大約2,450 | 同じ色の図形を1つの三角形配列にまとめて1回で描く（武者の「同じ色の円・多角形を1つの三角形配列にまとめ描き」の前例）。数と半透明の重なりを減らす。どちらが効くかを先に切り分ける |
| ドローコールが多すぎる（マテリアル・テクスチャの切り替え） | 宇宙飛行士の全体攻撃でドローコール約950・プリミティブ約17,000 → 25fps前後が約1秒続く。覚醒は11秒間ほぼ36fps | 同じマテリアル・同じテクスチャの描画をまとめる。全画面の重ね処理を必要な区間だけにする |
| 全画面のシェーダー・SubViewport | 武者の覚醒後の攻撃は1920×1080でさらに悪化（20ms超 39→78フレーム） | 低解像度のSubViewportで描いて拡大する／区間を短くする |
| 起動時のGDScriptでの画像処理 | 紳士のタイトルの部屋が起動のたびに2〜2.9秒停止（25枚の切り抜きをピクセル単位で処理） | 判定を1回にまとめてGodot内蔵の処理（`blit_rect_mask` 等）を使う／事前に作った素材にする |

その他:
- `_process` で毎フレーム新しい配列・辞書・Image・ShaderMaterialを作らない。
- `get_image()`（GPU からの同期の読み出し）は本番コードで使わない（検証ツールでも再生中は避ける）。
  - 承認済みの例外は1つだけ: 武者の覚醒後オーラ（`rbm_musha_aura.gd`）が、石畳の溝を辿るために戦闘背景を読む用途。次の条件をすべて守る:
    - 1戦闘につき必要な回数だけ（背景1枚につき1回）。毎フレーム・再生のたびには使わない。
    - 覚醒より前の準備の段階で行う（背景を RGBA8 の描画先へ写してから読む。約3ms。RGB8 の画像を直接読み出すと、起動して最初の1回だけドライバーの準備で約55ms止まる）。
    - 演出の再生中に同期の読み出しをしない。
    - 現在の実装: 写しは戦闘を始める前の画面で作る（覚醒が設定された武者の戦闘だけ）。準備されずに始まった戦闘では、戦闘画面を開いて約45フレーム後に作る。写しが出来て溝を辿り終えるまで、覚醒の演出は始まらない（§2.1 の「演出の開始の境界で待つ」。`background_ready()`）。写しが無い時に背景を GPU から直接読み出す処理は削除した（2026-10-08、QA-06）。写しが無いまま覚醒した状態から始まった時（通常の戦闘では起きない）は、写しを頼み、出来るまで溝・松明を省く。
  - この例外を、他の用途で `get_image()` を使う根拠にしない（「武者で使っているから本番で使ってよい」ではない）。新しく必要な時は、理由と実測を示してユーザーの承認を得る。
  - 規約より前から本番コードにある使用（戦闘画面の味方のカードの顔 `rbm_battle_ui_kit.gd`、挑戦の一覧の縮小画像 `rbm_challenge_list_style.gd`、紳士のタイトルの部屋）は、承認済みの例外ではない。見直しは別の課題。
- 大きなWAVは `load()` が速くても、`AudioStreamPlayer` の作成と合わせて事前読み込み（§2.1）に含める。

### 2.1 演出の素材は再生中に初めて読み込まない（初回の停止を作らない）
- **基準:** 演出の開始フレームと再生中に、同期の読み込み（ファイルの I/O）・初めてのデコード（画像・音の展開、GPU への転送）・初めての解析（JSON・モーションのデータ）を起こさない。起動して1回目の再生も、2回目以降と同じ時間で始まること（§3 のとおり同じ起動の中で同じ演出を複数回測り、1回目と2回目以降を比べる）。
- **新しい演出を作る・素材を足す時:** その演出が再生中に使う画像・音・モーション・データを、事前読み込みの宣言に含める。宣言に無い素材を再生中に初めて読み込む作りにしない。
- **現在の標準の実装:** 演出スクリプトの静的関数 `warm_paths(asset_id, kind)` で宣言する。共通部品 `rbm_presentation_warmup.gd`（ステージが持つ）が裏のスレッドで1件ずつ読み込んで保持する。宣言漏れは `tests/bossmaker/test_rbm_presentation_warmup.gd`（初回の再生で、事前に持っていない画像・データを読むと失敗する）が検出する。このテストを削らない・弱めない。仕組みを作り替える時も、上の基準と宣言漏れの検出は保つ。
  - 読み始める時: 戦闘を始める前の画面（Creator の最終確認・クリアチェックの確認・挑戦のボスの確認）が、ボス・外見・味方・技・覚醒が確定した時点でステージの `prepare_presentations()` を呼ぶ（その画面のフレームを重くしないよう、準備は次のフレームから2フレームに分けて行う）。戦闘が始まるとその戦闘で計画し直し、読み終えた物はそのまま使う。準備されずに始まった戦闘だけ、戦闘画面を開いて30フレーム後に読み始める。
  - 読む順: 戦闘の流れ（`rbm_battle.gd`）で早く要る可能性がある順。戦闘を開くと同時に再生されうる物（1ターン目のターン開始時の指定行動 → 開始時に条件を満たす覚醒 → 味方全員より速いボスの技）→ 最初の入力で再生されうる物（開始時に使える味方の専用の技 → HP の条件を持つ覚醒）→ ボスの1ターン目の技・味方の被弾の姿勢 → それ以降。
  - 手放す時: 戦闘を出る時（`release_presentations()`）と、確認画面を離れる時。
- **間に合わない時は、演出の開始の境界で待つ（同期で読まない）:** 事前読み込みを早く始めるのが第一の対策。それでも素材を読み終えていない時（戦闘を始める前の画面からすぐに戦闘を始めた、遅い PC 等）は、その行動の演出を始める境界で、その演出が宣言した素材（`warm_paths()`）が揃うまで待つ。現在の実装は `rbm_battle_stage.gd` の `_start_dedicated()`（専用の演出の入口はここに1つ）と `rbm_presentation_warmup.gd` の `ensure()`（足りない素材を読む順の先頭へ回す）。武者の覚醒は、オーラの背景の写しも条件にする。
  - 待つ間も、その行動は再生中のまま。presenter はその行動の impact／finished を待つので、HP の表示・次の行動・ターンの終わり・覚醒の後の処理・別の演出は先へ進まない（映像だけが遅れて追いかける形にしない）。戦闘の計算・乱数は変えない。
  - 待つのは、その演出の素材だけ（全素材の事前読み込みの完了は待たない）。固定の時間では待たない（実際に読み終えたかを毎フレーム確かめる）。揃ったのを見たフレームの次のフレームで始める（読み終えた画像の GPU への転送を、演出の最初のフレームに重ねない）。
  - メインスレッドを止めない・ゲーム全体の入力を止めない（コマンドの欄は、演出の再生中と同じ扱い）。
  - 今の PC で事前読み込みが間に合うからといって、この待ちを外さない（遅い環境で同期の読み込みを起こさないための安全策）。
  - 実測（2026-10-08、参照機・1280×720、前の画面の次のフレームで戦闘を始めた最速の経路）: 戦闘を開いてから演出が始まるまで、武者 開幕の単体・1ターン目の指定行動 0.32〜0.35秒、竜 開幕の単体 0.47秒、武者 開始時の覚醒 0.18〜0.20秒、紳士 開幕の単体・開始時の覚醒 0.13〜0.15秒、ヒーラーの全体回復（最初の入力）0.03秒。どの経路も、演出の開始時に未読の素材 0、開始フレーム 15〜17.5ms、演出中の 33ms超なし、待つ間のフレーム 10〜21ms。入力の後に始まる演出（最速の入力の後のボスの演出・最初の攻撃での覚醒）は、今の PC では待たずに始まる。詳しくは [QUALITY_AUDIT_STANDARD_DELTA.md](QUALITY_AUDIT_STANDARD_DELTA.md) の QA-06 の記録。
  - テスト: 演出の契約テストは、事前読み込みが読み終えた状態で検証する（`tests/bossmaker/presentation_assets_ready.gd`）。待つ動き（待つ・待つ間に先へ進まない・取り消すと始まらない・揃っていればすぐ始まる）は `test_rbm_presentation_warmup.gd` が検証する。検証ツールで演出を直接流す時も、事前読み込みが読み終えてから流す（例: `tools/verify_gentleman_gpu.gd` の `warmed()`）。
- **停止を別の場所へ移さない:** 事前読み込みそのものが、戦闘画面を開く時・覚醒の始まり・別の画面など、ほかの瞬間に停止を作ってはいけない（同期の一括読み込みを戦闘開始へ移しただけ、は改善とみなさない）。裏で少しずつ読み、画面を開いた直後の重いフレームを避ける。修正の前後で、戦闘画面を開いた後の数秒のフレーム時間も測って確かめる。
- **メモリ（VRAM を際限なく増やさない）:**
  - 保持するのは戦闘の間だけ。ボス・外見（覚醒の前後）・味方の単位で計画し、その戦闘で使わない技・外見の分は持たない。戦闘を出る・ボスが替わる時に手放す。
  - 現在の実装（2026-10-08 実測）: 事前読み込みの素材は、戦闘を出ると手放す（戦闘を出た直後のテクスチャメモリは、事前読み込みが無い場合と同じ）。ただし戦闘を始める前の画面（最終確認・確認画面）を表示している間は、次の戦闘のために持つ（武者 +46〜73MB、竜 +56MB。戦闘から戻ると、その画面のためにもう一度読み込む）。QA-05 の着弾画像は、これとは別に戦闘画面が残る間保持する（QA-05 の仕組みのまま）。
  - 大きな素材は枚数の上限を決める（例: 紳士の着弾画像は最大3枚、`rbm_gentleman_impact_sheets.gd`）。
  - 事前読み込みを増やす時は、全演出を一通り再生した後のテクスチャメモリ（`Performance.RENDER_TEXTURE_MEM_USED`）の増分を修正前と比べ、保持する期間・手放す条件・その素材を事前に持つ必要性と一緒に報告する。
  - 基準値（参照機・1280×720）: 第1段で計測した戦闘中の値は武者 +19〜23MB、他のボス +3〜11MB。第2段（戦闘の前から読む形）では、戦闘を始める前の画面で武者 +46〜73MB・竜 +56MB、戦闘中は武者 +26.6MB（覚醒まで再生した時）。**QA-06 の値として承認**（2026-10-08、ユーザー）。ただし将来の絶対の VRAM 予算ではなく、全演出に機械的に当てはめる上限でもない判断の基準。新しい事前読み込みでこの基準から明らかに増える時は、上の4点（増分・保持期間・解放条件・必要性）を示してユーザーの承認を得る。
  - 確認画面の出入り（2026-10-08 実測）: Creator の最終確認へ入って戦闘を始めずに戻る、を10回、クリアチェックの確認へ入って戻る、を10回繰り返しても、テクスチャメモリは毎回同じ値に戻り、増え続けない（STEP4 41.6MB → 確認画面 118.5〜118.6MB → 戻ると 41.7〜41.9MB、最後に 41.9MB）。
- **GPU 側の初回の準備（シェーダーのコンパイル等）:** 事前読み込みでは消えない。対処する前に、実GPUで原因を計測して確定する（推定のまま「画面外で一度描いておく」仕組みを入れない）。対処した時も、停止を戦闘開始など別の瞬間へ移していないことを実測で確かめる。未対処の例: 宇宙飛行士の覚醒の初回（[QUALITY_AUDIT_STANDARD_DELTA.md](QUALITY_AUDIT_STANDARD_DELTA.md) N-07）。

## 3. 計測のしかた

- **実時間で測る。** 演出の再生中、フレームごとの経過時間（`Time.get_ticks_usec()` の差）を記録し、平均fps・1%low・最悪フレーム・20ms／33ms超の数を出す。再生中は画面の読み出し・ファイル保存・print をしない。
- 同じ演出を同じ起動の中で**2回**測る。1回目だけ遅いなら初回の読み込み・コンパイル、毎回遅いなら再生のたびの処理か描画そのもの。
- 遅いフレームが演出開始から何秒の所かを記録すると、どの層（VFX・煙・シェーダー）が原因か分かる。`Performance.RENDER_TOTAL_OBJECTS_IN_FRAME`／`RENDER_TOTAL_DRAW_CALLS_IN_FRAME`／`RENDER_TOTAL_PRIMITIVES_IN_FRAME` を一緒に記録する。
- 1280×720と1920×1080の両方で測る（全画面のシェーダーは大きい画面で重くなる）。
- 見た目の確認には `--fixed-fps 30` で一定間隔に切り出した一覧画像を使ってよい（時間が固定されるので毎回同じ場面になる）。ただし性能の判断には使わない。

## 4. 構造のルール

- 演出は「振り分け（`rbm_battle_stage.gd`）→ 技ごとの専用スクリプト → 共通部品」。`rbm_battle_stage.gd` に技固有の処理を足さない。if分岐の羅列を増やさない。
- 共通部品（揺れ・Hit Stop・残像・衝撃波・破片・移動・SE・Flash・後始末・素材の事前読み込み）は共通化する。現状、揺れは演出ごとに別々に書かれている（新しく作る時は共通部品へ）。
- 戦闘状態・乱数・保存データに触れない（`simulation_unchanged` を検証する）。
- コードの見た目の美しさだけを理由に既存コードを変えない。大きな構造の変更は、今後の制作を著しく妨げる時だけ、範囲を区切って行う。

## 5. テストと実GPU検証

- テストの選び方（レベル・全GUTの条件・想定外の失敗の扱い・報告の形）は [TESTING.md](TESTING.md) に従う。テストを削る・弱めることでPASSさせない。
- 演出・UIを変えたら、関連する `tools/verify_*` の実GPU検証も行う（TEST BATTLE・クリアチェック・挑戦の3画面、5属性、カウンター、中断、1280×720以外のウィンドウ）。
- 検証ツールの色の判定は、命中後の短い時間帯（例: 0.10〜0.50秒）の毎フレームで数え、演出前の画面との差で判定する。判定を甘くして通さない（演出を消すと失敗することを確かめる）。
- 既存の検証ツールの既知の問題: `verify_real_skills_gpu.gd` はHPと無関係の構造チェック3件がHEADでも失敗、狼のツールは固定1時点の判定のまま（現状は余裕を持って合格）。
- 既存の検証ツールの既知の問題（2026-10-08確認、別の作業で直す。演出側を変えて通さない。先に「今の正しい仕様に検証を合わせるべき問題か」を確かめる）:
