# Visual Examples（APPROVED／REJECTED／BEFORE／AFTER）

文章だけで品質を判断しないために、**このゲーム自身の**承認・却下・修正前後の比較を残し、そこから原理を学ぶための置き場。
（2026-10-07時点では、まだ例は登録していない。このファイルは運用の決まりだけを持つ）

---

## 1. 何を残すか

| 種類 | 内容 | 主に学ぶこと |
|---|---|---|
| APPROVED | ユーザーが動画で承認した演出・画面の最終版 | 何が効いているか（なぜ良いか） |
| REJECTED | ユーザーが却下した案 | 何がダメだったか（なぜ却下されたか） |
| BEFORE／AFTER | 1つの修正の前と後。同じ場面・同じ条件・同じコマで撮る | 直したことで何が良くなったか、悪くなっていないか |

- 残すのは **Makers & Challengers の素材だけ**。
- 却下された理由は、承認された結果と同じくらい大事。理由の記録が無い例は残さない。

---

## 2. 置き方

```
docs/quality/examples/
  README.md                      この運用の説明と、下の台帳
  <日付>_<対象>_<種類>/           例: 2026-09-22_musha-aura_APPROVED/
    note.md                      下の §3 の記録
    sheet.png                    一覧画像（コマ送り）
    clip.webm など               短い動画（数秒）
```

- 一覧画像（PNG）を優先する。動画は数秒に切る。
- 大きな動画はリポジトリに入れず、置き場所（パス・URL）だけを note.md に書く。Git LFS などの導入はユーザーの判断。
- 撮影条件をそろえる: 解像度（1280×720が基本）、`--fixed-fps` か実時間か、同じ戦闘の場面。

---

## 3. 1つの例に付ける記録（note.md）

```
種類: APPROVED / REJECTED / BEFORE / AFTER
対象: （ボス・技・画面）
日付・commit:
撮影条件: （解像度、fixed-fps か実時間か、画面）
判断した人: （ユーザー）
判断の理由: （ユーザーの言葉をできるだけそのまま）
学んだ原理: （Pose／Timing／Spacing／Silhouette／Value／Color／Shape／Composition／Audio などの言葉で。
             関係する規約の章: 例 ANIMATION_CRAFT §2、COMBAT_PRESENTATION §5.5）
使ってはいけない学び方: （例: 「この時間割を他のボスにそのまま使う」）
```

---

## 4. 学び方

- APPROVED から: 何が効いているかを、原理の言葉で書く。「武者と同じ形・同じ時間割にする」のような**そのままのコピーはしない**（技・ボスごとに固有の演出にする方針。ART_DIRECTION §1）。
- REJECTED から: どの原理に反していたかを書く。同じ失敗を新しい演出で繰り返していないかを確かめる時に使う。
- BEFORE／AFTER から: 直したことでプレイヤーが感じる差が本当にあるか、他の部分を壊していないかを確かめる。
- AIは、例を「正解のテンプレート」として機械的に当てはめない。最終判断はユーザーが映像を見て行う。

---

## 5. 禁止

- 他のゲーム・作品の画像・動画をリポジトリに置かない。参考にする時は、作品名・該当の時刻・URLを書くだけにして、原理だけを取り出す。
- 参考作品の固有のデザインを複製しない。
- 承認済みの例を、規約の数値を正当化するためだけに使わない。
